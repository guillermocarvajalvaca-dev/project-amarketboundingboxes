\begin{abstract}
Este trabajo construye un \emph{pipeline} automático de anotación monoclase
(\texttt{0: product}) a partir del catálogo público de Amarket: 655 imágenes
aceptadas, splits 459/98/98 sin fuga de SKU, y un detector YOLO11n
(Experimento A) evaluado sobre prueba bloqueada. Un replanteo del alcance,
comunicado por el docente durante el desarrollo, exige además identificar
\emph{qué} producto aparece en escenas multiproducto tipo caja de
supermercado. Para responder sin invalidar el contrato monoclase congelado
(\texttt{class\_id=0} en todo el dataset; SKU y nombre nunca como clase, dado
que el catálogo tiene aproximadamente una muestra por SKU), se documenta una
decisión de alcance no congelada (ADR-006) y se implementa una arquitectura
de dos etapas: el mismo detector monoclase localiza cada objeto, y una
segunda etapa de \emph{retrieval} visual (SIFT contra un catálogo de 655
referencias) resuelve la identidad sin reentrenar el detector ni clasificar
por SKU. El detector, aumentado con 197 escenas sintéticas multiproducto
(de una meta de 655, limitación declarada), alcanza mAP@50-95=0.9715 sobre
prueba real bloqueada. La identificación, evaluada de forma cerrada sobre
481 placements sintéticos, alcanza 84.62\,\% top-1 y 92.31\,\% top-5, con
0\,\% de tasa \texttt{UNKNOWN}. Se reportan también los errores de identidad,
concentrados en variantes de una misma línea de producto y envases de baja
textura.
\end{abstract}

\section{Introducción}

El etiquetado manual de \emph{bounding boxes} no escala. Anotar a mano cada
producto de un catálogo comercial exige un esfuerzo proporcional al número de
imágenes, es costoso de verificar y difícil de reproducir: dos anotadores
distintos producen cajas distintas sobre la misma fotografía.

Este trabajo construye un \emph{pipeline} automático de anotación a partir de un
catálogo real. Las fotografías de producto de un comercio electrónico presentan
una regularidad aprovechable: muestran un único artículo aislado sobre fondo
uniforme o transparente. Esa regularidad permite derivar la caja delimitadora de
forma determinista a partir de los píxeles extremos del producto, sin
intervención humana y sin ambigüedad entre anotadores.

El objetivo base es un dataset de detección \textbf{monoclase}. La única clase
YOLO es \texttt{0: product}. El SKU, el nombre y la descripción se conservan
como metadatos de procedencia y trazabilidad, no como clases YOLO: el detector
resuelve \emph{dónde} está el producto, no \emph{cuál} es.

Durante el desarrollo, el docente replanteó el objetivo funcional final para
simular una caja de supermercado: dada una escena con varios productos, el
sistema debe localizar cada artículo \emph{e} identificar cuál es. Convertir
\texttt{class\_id} en un identificador de SKU es estadísticamente inviable
--el catálogo aporta aproximadamente una muestra por SKU, insuficiente para
construir train/val/test por clase-- y además violaría el contrato monoclase
congelado del dataset base. La respuesta documentada (Anexo/ADR-006, no
congelado) es una arquitectura de \textbf{dos etapas}: el detector monoclase
localiza, y una segunda etapa de \emph{retrieval} visual identifica contra un
catálogo de referencia, sin reentrenar ni reclasificar el detector.

\section{Marco teórico}

\subsection{Detección de objetos y formato YOLO}

YOLO codifica cada caja como
\texttt{<class\_id> <x\_c> <y\_c> <w> <h>}, valores normalizados a $[0,1]$
(independientes de la resolución); en el dataset monoclase, \texttt{class\_id}
es siempre \texttt{0}. Dada una imagen $W\times H$ y los píxeles extremos
inclusivos $x_{\min},x_{\max},y_{\min},y_{\max}$ del producto, con borde
semiabierto ($x_{\max}+1$, $y_{\max}+1$, evitando el truncamiento de un
píxel):
\begin{equation}
x_c=\tfrac{x_{\min}+x_{\max}+1}{2W},\quad
y_c=\tfrac{y_{\min}+y_{\max}+1}{2H},\quad
w=\tfrac{x_{\max}-x_{\min}+1}{W},\quad
h=\tfrac{y_{\max}-y_{\min}+1}{H}
\label{eq:yolo}
\end{equation}
Los cuatro valores se escriben con seis decimales, precedidos de
\texttt{class\_id=0}.

\subsection{Datasets de retail densamente anotados}

\textbf{SKU-110K}~\cite{goldman2019} (11.762 imágenes, $\sim$1,73M de cajas)
anota estantería densa como un \textbf{único tipo de objeto}: localización en
escenas densas, no identificación (el «110K» refiere a la diversidad de SKU
en escena, no a clases anotadas). \textbf{MVTec D2S}~\cite{mvtecd2s} aporta
segmentación de instancias con separación deliberada train/eval.
\textbf{RP2K}~\cite{peng2020} aborda reconocimiento \emph{fine-grained} entre
artículos. La diferencia con este trabajo es de escena y objetivo: los tres
operan sobre estantería en tienda; aquí se parte de catálogo con un producto
aislado sobre fondo controlado, lo que habilita la caja determinista, y la
identificación (cuando se requiere) se resuelve aparte, por
\emph{retrieval}, no por clases.

\section{Metodología}

\subsection{Visión general del \emph{pipeline}}

Seis etapas con propietario y contrato definidos: (1) \textbf{adquisición}
(\texttt{src/scraper\_extraction.py} descarga el catálogo público con
procedencia trazable); (2) \textbf{validación de fondo} (producto aislado,
fondo uniforme o transparente; rechazos registrados con motivo);
(3) \textbf{píxeles extremos} sobre la máscara del producto;
(4) \textbf{conversión a YOLO}; (5) \textbf{particionado} 70/15/15 sin fuga;
(6) \textbf{modelado y evaluación} (\emph{fine-tuning}, evaluación e
inferencia en CPU).

\subsection{Particionado, entrenamiento y evaluación}

El dataset se divide 70/15/15 por \emph{grupos} (SKU, hash de bytes, grupo de
duplicados o linaje), no por imagen suelta, para que ninguna partición filtre
al resto y las métricas no queden infladas por memorización. Se parte de un
detector preentrenado (YOLO11n), ajustado sobre entrenamiento y seleccionado
sobre validación; semilla fija \texttt{42}, hiperparámetros en configuración
versionada, nunca embebidos en código. Prueba permanece bloqueada durante todo
el ajuste y se consulta una sola vez, sin realimentar ninguna decisión de
diseño. La inferencia final se verifica también en CPU, sin CUDA.

\subsection{Aumentación sintética y retrieval de identidad}

Experimento B añade escenas sintéticas multiproducto: composiciones
deterministas de cutouts \emph{train-only}, con geometría de oclusión
controlada y verificación de hash. Meta contractual: 655 escenas; la corrida
completa se detuvo en SYN\_0198 al agotar el presupuesto de búsqueda
estructurado \emph{respetando} el límite de oclusión, y se congelan las 197
escenas válidas (limitación declarada), sin tocar validación/prueba (98/98
reales).

La segunda etapa recibe el \emph{crop} de cada caja YOLO y lo compara, vía
descriptores SIFT y \emph{matching} por fuerza bruta con prueba de razón de
Lowe (0.75), contra un catálogo de 655 referencias (cutout de entrenamiento
o foto real), indexadas una sola vez. Se devuelve el SKU con más
coincidencias válidas; por debajo de un umbral mínimo se declara
\texttt{UNKNOWN}. Determinista, sin entrenamiento ni pesos adicionales:
SIFT/ORB ya están disponibles en el entorno; se descartó un backend de
\emph{embeddings} preentrenados por exigir descargar pesos ausentes
localmente.

\section{Resultados}

\subsection{Detección: Experimento A vs. Experimento B}

Experimento A: 459 imágenes reales, un producto por imagen, YOLO11n, 40/40
épocas, CPU (peso \texttt{sha256:9149dfef...}, evidencia en
\texttt{docs/evidence/G4\_STATUS.md}). Experimento B: 656

\texttt{mAP@50-95} en validación (B0: P=0.998, R=0.990, mAP@50=0.995,

\section{Discusión}

La aumentación sintética multiproducto mejora \texttt{mAP@50-95} en
validación (0.987$\to$0.991) y el detector T1 mantiene un desempeño casi
perfecto sobre prueba real bloqueada (0.9715), pese a entrenar con solo 197
de las 655 escenas planificadas. La tarea de localización monoclase parece
saturada para este dominio: producto aislado sobre fondo controlado, una
sola clase, sin ambigüedad de forma.

La identificación es la tarea genuinamente difícil. El 84.6\,\% de exactitud
top-1 no es una cifra intercambiable con las métricas de detección: mide un
problema distinto (identidad de instancia por \emph{retrieval}, no
localización) y, como se advierte arriba, en un dominio cerrado. Los errores
observados (figura~\ref{fig:errores}) no son aleatorios: se concentran en (a)
variantes de una misma línea de producto, donde el empaque difiere solo en
texto o color pequeño (mismo caso que llevó a descartar \texttt{class\_id}
por SKU en primer lugar), y (b) envases lisos con poca textura local, donde
SIFT tiene pocos puntos de interés que extraer. Ambos son límites conocidos y
documentados de los descriptores locales clásicos, no una falla de
implementación: la verificación cruzada entre el subconjunto de 20 escenas
usado para elegir el \emph{backend} y la evaluación completa de 481
\emph{placements} reprodujo exactamente los mismos resultados fila por fila
cuando se usó el mismo peso, lo que descarta una discrepancia de código.

\section{Limitaciones}

La derivación determinista de cajas por píxeles extremos sigue dependiendo de
que la fotografía de \emph{catálogo} muestre un único producto sobre fondo
uniforme o transparente; esa etapa no cambia. La novedad de este trabajo ---la
composición sintética y la identificación--- sí opera sobre escenas
multiproducto, pero con límites propios:

\begin{itemize}
  \item \textbf{Dataset sintético incompleto (197/655).} La corrida completa
        falló en SYN\_0198 por agotamiento del presupuesto de búsqueda
        estructurado, respetando el límite de oclusión en vez de violarlo.
        Las 197 escenas usadas son todas de dificultad \emph{basic}
        (2--3 objetos); el detector no fue expuesto durante el entrenamiento
        a las densidades \emph{medium/hard/extreme} planificadas.
  \item \textbf{Evaluación de identidad cerrada.} El 84.6\,\% top-1 mide
        \emph{retrieval} contra el catálogo del que las escenas derivan, no
        generalización a fotografías nuevas de una caja real.
  \item \textbf{SIFT confunde variantes de línea y envases lisos}, como se
        discute arriba; no hay mecanismo de \emph{fine-tuning} sobre esos
        casos difíciles en este trabajo.
  \item El dataset procede de un único comercio, por lo que su diversidad
        visual está acotada por el catálogo de origen y sus convenciones
        fotográficas.
\end{itemize}

\section{Conclusiones}

El objetivo de localización monoclase se cumple con alta fiabilidad tanto en
el dominio de producto único (Experimento A, mAP@50-95=0.9929 en prueba) como
en el multiproducto aumentado sintéticamente (Experimento B/T1,
mAP@50-95=0.9715 en prueba), sin necesidad de convertir \texttt{class\_id} en
un identificador de producto --- decisión que además habría sido inviable
dado el catálogo disponible (aproximadamente una muestra por SKU). La
arquitectura de dos etapas responde al replanteo docente preservando el
contrato monoclase congelado: localizar y identificar son problemas
distintos, resueltos por componentes distintos, con sus propias métricas y
sus propias limitaciones. La identificación por \emph{retrieval} visual es
funcional (84.6\,\% top-1, 92.3\,\% top-5) pero no está lista para
generalizar fuera del catálogo cerrado evaluado; una arquitectura de
\emph{embeddings} aprendidos, hoy descartada por no haber pesos
preentrenados disponibles localmente, es la vía natural para mejorarla.

\section{Reproducibilidad}

\subsection{Entorno}

Experimento A: Python 3.11.9, dependencias fijadas en \texttt{requirements.txt},
CPU. Experimento B (GPU): entorno \texttt{ComputerVision} (WSL2 Ubuntu),
Python 3.12.13, PyTorch 2.13.0+cu126, Ultralytics 8.4.120, CUDA 12.6, NVIDIA
GeForce RTX 4050 Laptop (6\,GB). La identificación usa OpenCV 5.0.0
(\texttt{SIFT\_create}, \texttt{BFMatcher}), ya presente en el entorno GPU sin
instalación adicional.

\subsection{Comandos}

El flujo completo se ejecuta desde la línea de órdenes, sin depender de
\emph{notebooks} (el \emph{notebook} de CPU es solo demostración final):

{\small\begin{verbatim}
# Experimento A (CPU)
python src/train.py    --config configs/baseline.yaml --data configs/dataset.yaml \
                        --output-dir outputs/runs/baseline --seed 42
python src/evaluate.py --model <peso> --data configs/dataset.yaml --split test \
                        --allow-test --output-dir outputs/evaluation/baseline

# Experimento B (GPU): sintetico (ADR-005) + entrenamiento/eval/identificacion (ADR-006)
python -m src.data.assign_synthetic_sources --scene-plan <plan> \
       --cutout-manifest <manifest> --output <assignments.csv>
python -m src.data.make_synthetic_scenes --assignments <assignments.csv> \
       --cutout-root <cutouts> --output-root <synthetic> --manifest <scene_manifest.csv> \
       --cutout-manifest <manifest> --generator-commit <sha>
python src/train.py    --config configs/experiment_b_gpu_t1.yaml \
                        --data <dataset_wsl.yaml> --output-dir <run_t1> --seed 42
python src/evaluate.py --model <run_t1>/weights/best.pt --data <dataset_wsl.yaml> \
                        --split test --allow-test --output-dir <test_eval_t1>
python src/predict.py  --model <run_t1>/weights/best.pt --input <escena.jpg> \
                        --catalog catalog_identity.csv --output-dir <resultados>
\end{verbatim}}

\subsection{Determinismo}

La semilla global es \texttt{42}. Cada ejecución registra la configuración
resuelta, la versión del entorno y el hash del peso empleado, de modo que una
evaluación repetida sobre el mismo peso produce métricas idénticas.
