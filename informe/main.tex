\begin{abstract}

El presente trabajo desarrolla un \emph{pipeline} reproducible para la
generación automática de \emph{bounding boxes} y el entrenamiento de un detector
de productos a partir de imágenes reales del catálogo público de AMARKET.
El problema se formuló inicialmente como una tarea de detección monoclase,
donde la clase \texttt{0: product} representa cualquier producto visible,
mientras que el SKU, nombre y descripción se conservan exclusivamente como
metadatos de procedencia.

La línea base se construyó a partir de 655 imágenes reales, particionadas de
forma determinista con semilla 42 en 459 imágenes de entrenamiento,
98 de validación y 98 de prueba. Las cajas se obtuvieron a partir de los
píxeles extremos del producto y se transformaron al formato YOLO mediante una
convención de bordes semiabiertos.

El modelo gobernante de la línea base corresponde a YOLO11n. Sobre las
98 imágenes del conjunto de prueba obtuvo una precisión de 1,0, un
\emph{recall} de 1,0, un F1 de 1,0, un mAP@0.5 de 0,995 y un
mAP@0.5:0.95 de 0,992875. La evaluación final se verificó adicionalmente
en CPU. Como extensión, la segunda fase del proyecto introduce escenas
sintéticas multiproducto manteniendo intacta la línea base real.

\end{abstract}

% =====================================================================
\section{Introducción}
% =====================================================================

El etiquetado manual de \emph{bounding boxes} representa uno de los principales
costos en la construcción de datasets para detección de objetos. Anotar
manualmente cada producto de un catálogo comercial requiere un esfuerzo
proporcional al número de imágenes, introduce variabilidad entre anotadores y
dificulta la reproducción exacta del dataset.

Este proyecto desarrolla un \emph{pipeline} automático de anotación utilizando
imágenes de productos provenientes de AMARKET. Las fotografías del catálogo
presentan una característica aprovechable: en una gran proporción de los casos
muestran un único producto sobre fondo uniforme o transparente. Esta regularidad
permite derivar de manera determinista una caja delimitadora a partir de los
píxeles pertenecientes al producto.

El problema se formula como una tarea de detección \textbf{monoclase}. La única
clase utilizada por el detector es:

\begin{center}
\texttt{0: product}
\end{center}

El SKU, nombre, descripción y demás atributos comerciales no representan clases
del modelo. Estos campos se conservan como metadatos para garantizar la
procedencia, trazabilidad y reproducibilidad de cada activo.

La primera fase del proyecto establece una línea base real, mientras que la
segunda fase amplía el problema hacia composiciones multiproducto sintéticas sin
alterar los conjuntos reales de validación y prueba.

% =====================================================================
\section{Objetivos}
% =====================================================================

\subsection{Objetivo general}

Construir un \emph{pipeline} reproducible para generar automáticamente
anotaciones de productos en formato YOLO y evaluar un detector de objetos sobre
un dataset real proveniente de AMARKET.

\subsection{Objetivos específicos}

\begin{itemize}

    \item Obtener y preservar la procedencia de los activos utilizados.

    \item Validar las imágenes antes de incorporarlas al dataset.

    \item Obtener automáticamente las coordenadas extremas del producto.

    \item Convertir las cajas delimitadoras al formato normalizado de YOLO.

    \item Construir particiones de entrenamiento, validación y prueba evitando
    fuga de información.

    \item Entrenar y evaluar una línea base de detección monoclase.

    \item Mantener trazabilidad entre imágenes, anotaciones, configuración,
    métricas y artefactos del modelo.

    \item Extender el problema hacia escenas multiproducto mediante generación
    sintética controlada.

\end{itemize}

% =====================================================================
\section{Marco teórico}
% =====================================================================

\subsection{Detección de objetos}

La detección de objetos combina dos problemas: la localización espacial de una
instancia dentro de una imagen y la asignación de una categoría. La localización
se representa normalmente mediante una caja delimitadora o
\emph{bounding box}.

En el presente trabajo todas las instancias pertenecen a una única categoría,
\texttt{product}. Por tanto, el reto principal es determinar correctamente la
posición y extensión espacial del producto.

% ---------------------------------------------------------------------

\subsection{Formato YOLO}

El formato YOLO representa cada objeto mediante una línea:

\begin{center}
\texttt{<class\_id> <x\_center> <y\_center> <width> <height>}
\end{center}

Las coordenadas geométricas se normalizan respecto a la anchura y altura de la
imagen, por lo que sus valores se encuentran en el intervalo $[0,1]$.

En este proyecto:

\begin{center}
\texttt{class\_id = 0}
\end{center}

para todas las anotaciones.

% ---------------------------------------------------------------------

\subsection{Datasets de retail}

\textbf{SKU-110K}~\cite{goldman2019} constituye un referente en detección de
productos en escenarios de retail densamente poblados. Contiene 11.762 imágenes
y aproximadamente 1,73 millones de cajas delimitadoras. La tarea principal es
la localización de productos en escenas densas.

\textbf{MVTec D2S}~\cite{mvtecd2s} aborda productos de supermercado mediante
segmentación de instancias y proporciona escenarios controlados para
entrenamiento y evaluación.

\textbf{RP2K}~\cite{peng2020} se orienta al reconocimiento
\emph{fine-grained} de productos minoristas.

A diferencia de estos datasets, la línea base de AMARKET utiliza inicialmente
fotografías de catálogo con productos aislados. Esta característica permite
automatizar la generación de cajas delimitadoras de forma determinista.

\section{Metodología}
% =====================================================================

\subsection{Visión general del pipeline}

La construcción del dataset sigue las siguientes etapas:

\begin{enumerate}

    \item \textbf{Adquisición y procedencia.}

    Se recopilan activos públicos de AMARKET conservando identificadores,
    enlaces, hashes y metadatos necesarios para garantizar trazabilidad.

    \item \textbf{Validación de imágenes.}

    Se comprueba que cada imagen pueda decodificarse correctamente y que cumpla
    las condiciones establecidas para la línea base.

    \item \textbf{Obtención de la máscara del producto.}

    Se separa el producto del fondo mediante las características de transparencia
    o uniformidad disponibles en la fotografía.

    \item \textbf{Obtención de píxeles extremos.}

    Sobre la máscara se calculan los extremos:

    \[
    x_{\min},\quad x_{\max},\quad
    y_{\min},\quad y_{\max}
    \]

    \item \textbf{Conversión a formato YOLO.}

    Las coordenadas se transforman a centro, anchura y altura normalizados.

    \item \textbf{Particionado.}

    El dataset se divide de manera determinista en entrenamiento, validación y
    prueba.

    \item \textbf{Entrenamiento y evaluación.}

    Se realiza \emph{fine-tuning} de un detector YOLO11n y posteriormente se
    evalúa el modelo congelado sobre el conjunto de prueba.

\end{enumerate}

% ---------------------------------------------------------------------

\subsection{De píxeles extremos a coordenadas YOLO}

Sea una imagen de anchura $W$ y altura $H$, y sean
$x_{\min}$, $x_{\max}$, $y_{\min}$ y $y_{\max}$ los índices extremos del
producto.

Los límites máximos se consideran inclusivos. Para representar correctamente la
extensión del objeto se utiliza una convención de bordes semiabiertos.

Las coordenadas se calculan como:

\begin{align}

x_c &=
\frac{x_{\min} + x_{\max} + 1}{2W}
\\[4pt]

y_c &=
\frac{y_{\min} + y_{\max} + 1}{2H}
\\[4pt]

w &=
\frac{x_{\max} - x_{\min} + 1}{W}
\\[4pt]

h &=
\frac{y_{\max} - y_{\min} + 1}{H}

\end{align}

Cada anotación se escribe en formato YOLO precedida por:

\begin{center}
\texttt{class\_id = 0}
\end{center}

\subsection{Prevención de fuga de información}

La separación entre conjuntos no se realiza únicamente por nombre de archivo.
La procedencia de los activos se conserva mediante identificadores, hashes y
grupos de duplicados.

El objetivo es evitar que versiones del mismo producto o activos equivalentes
aparezcan simultáneamente en entrenamiento y evaluación.

Las verificaciones realizadas sobre el dataset canónico no detectaron:

\begin{itemize}

    \item clases inválidas;
    \item cajas inválidas;
    \item imágenes huérfanas;
    \item etiquetas huérfanas;
    \item fugas entre las particiones gobernantes.

\end{itemize}

\section{Entrenamiento}
% =====================================================================

La línea base gobernante utiliza la arquitectura:

\begin{center}
\textbf{YOLO11n}
\end{center}

El entrenamiento se realiza únicamente sobre el conjunto de entrenamiento y las
decisiones de selección de modelo se realizan utilizando el conjunto de
validación.

La partición de prueba permanece bloqueada durante el ajuste y se utiliza
únicamente en la evaluación final del modelo seleccionado.

La evaluación final fue ejecutada adicionalmente en CPU para verificar que la
inferencia no dependiera de CUDA ni de hardware especializado.

\subsection{Artefacto del modelo}

El modelo gobernante corresponde al artefacto de la línea base de la Fase 1.

% =====================================================================
\section{Extensión multiproducto: Fase 2}
% =====================================================================

La segunda fase del proyecto preserva íntegramente la línea base de la Fase 1 y
extiende el problema hacia escenas que contienen varios productos.

Para ello se definió un segundo experimento de entrenamiento que combina los
productos reales del conjunto de entrenamiento con escenas sintéticas
multiproducto.

La arquitectura experimental establece:

\begin{itemize}

    \item \textbf{Experimento A:} línea base real de la Fase 1.

    \item \textbf{Experimento B:} entrenamiento real más escenas sintéticas
    multiproducto.

\end{itemize}

Las imágenes reales de validación y prueba se mantienen inalteradas para
garantizar que la comparación entre experimentos utilice el mismo dominio de
evaluación.

La generación sintética se define exclusivamente a partir de activos pertenecientes
al conjunto de entrenamiento, evitando utilizar productos procedentes de
validación o prueba.

El diseño gobernante contempla 655 escenas sintéticas y 3287 colocaciones de
productos distribuidas entre diferentes niveles de dificultad y cantidad de
objetos por escena.

Las cajas de las escenas sintéticas se calculan a partir de la máscara visible
final de cada producto después de aplicar composición y oclusión.

Los resultados cuantitativos del Experimento B deben incorporarse únicamente
cuando su ejecución y evidencia correspondiente se encuentren formalmente
cerradas.

% =====================================================================
\section{Discusión}
% =====================================================================

Los resultados de la línea base demuestran que las características visuales de
las fotografías de catálogo permiten construir automáticamente anotaciones de
alta consistencia.

El desempeño obtenido debe interpretarse considerando que las imágenes de la
línea base contienen principalmente productos aislados sobre fondos
controlados. Por ello, el alto rendimiento del detector no implica
necesariamente el mismo comportamiento en escenas densas, con oclusiones,
múltiples productos o fondos complejos.

Precisamente esta limitación motiva la extensión planteada en la Fase 2, donde se
introducen composiciones multiproducto para analizar la capacidad de
generalización del detector frente a escenarios progresivamente más complejos.

% =====================================================================
\section{Limitaciones}
% =====================================================================

La línea base presenta varias limitaciones:

\begin{itemize}

    \item El dataset real procede de un único comercio electrónico.

    \item Las convenciones fotográficas del catálogo reducen la diversidad de
    fondos y condiciones de iluminación.

    \item Las imágenes reales de la Fase 1 representan principalmente productos
    aislados.

    \item Las métricas elevadas obtenidas en el conjunto de prueba no deben
    extrapolarse automáticamente a fotografías de estanterías o escenarios
    multiproducto.

    \item La extensión sintética permite introducir oclusión y múltiples
    productos, pero una escena sintética no sustituye completamente la
    variabilidad de una fotografía real capturada en tienda.

\end{itemize}

Por estas razones, los resultados de cada experimento deben interpretarse dentro
del dominio específico sobre el cual fue evaluado.

% =====================================================================
\section{Conclusiones}
% =====================================================================

El proyecto demuestra que es posible automatizar de forma reproducible la
generación de \emph{bounding boxes} a partir de fotografías de catálogo cuando
existen condiciones visuales suficientemente controladas.

La línea base fue construida utilizando 655 imágenes reales de AMARKET,
manteniendo trazabilidad de los activos y una división determinista en
459 imágenes de entrenamiento, 98 de validación y 98 de prueba.

El modelo YOLO11n seleccionado alcanzó una precisión y un \emph{recall} de
1,0, un mAP@0.5 de 0,995 y un mAP@0.5:0.95 de 0,992875 sobre el conjunto
real de prueba.

Además del resultado del modelo, uno de los principales aportes del proyecto es
la reproducibilidad del proceso: adquisición, validación, generación de cajas,
particionado, entrenamiento y evaluación se encuentran separados en etapas
auditables y versionadas.

La segunda fase amplía el alcance hacia escenas multiproducto sintéticas,
manteniendo intacta la línea base real para permitir comparaciones controladas
entre ambos escenarios.

\section{Reproducibilidad}
% =====================================================================

\subsection{Entorno}

La ejecución del proyecto se realiza en un entorno Python versionado. Para las
validaciones recientes del proyecto se utilizó Python 3.11.9.

La configuración, scripts, manifiestos y evidencia se conservan dentro del
repositorio, permitiendo reconstruir las distintas etapas del pipeline.

% ---------------------------------------------------------------------

\subsection{Comandos principales}

El pipeline se ejecuta mediante scripts independientes desde línea de comandos.

Ejemplos de las operaciones principales son:

\begin{verbatim}

python src/scraper_extraction.py --smoke-test --limit 3

python src/data/make_boxes.py

python src/data/make_splits.py

python src/train.py --config configs/baseline.yaml

python src/evaluate.py --weights <peso> --split test

python src/predict.py --weights <peso> --source <imagen>

\end{verbatim}

La semilla utilizada para el particionado gobernante es:
